# Automated Identification of Complex PCI From Cardiac Catheterization Reports Using Large Language Models

## Overview

This repository contains the code used to evaluate large language models (LLMs) for identifying percutaneous coronary intervention (PCI) and extracting procedural characteristics used to classify complex PCI from unstructured cardiac catheterization reports.

The study evaluated three open-source language models:

* Llama 3.3 70B
* Meditron-7B
* BioMistral-7B

The evaluation consisted of two sequential tasks:

1. **PCI identification:** determine whether a cardiac catheterization report described a coronary PCI procedure.
2. **Complex PCI extraction and classification:** among reports with gold-standard PCI, extract six procedural variables and use them to determine whether the procedure met criteria for complex PCI.

The study included 1,412 cardiac catheterization reports from three clinical sites within the Yale New Haven Health System. Reference-standard labels were generated by manual review and adjudication by clinicians. The clinical reports and patient-level reference-standard data are not distributed in this repository because of IRB and patient-privacy restrictions.

## Complex PCI definition

Six procedural variables were extracted from reports with gold-standard PCI:

* Number of vessels treated
* Number of lesions treated
* Number of stents implanted
* Total stent length
* Bifurcation PCI treated with two stents
* Chronic total occlusion

Each variable was converted into its corresponding complex PCI criterion:

* At least 3 vessels treated
* At least 3 lesions treated
* At least 3 stents implanted
* Total stent length greater than 60 mm
* Bifurcation PCI treated with two stents
* Chronic total occlusion

A procedure was classified as **complex PCI** when at least one criterion was present.

A procedure was classified as **non-complex PCI** only when all six criteria were available and none was present. If no criterion was positive but one or more variables were unavailable, complex PCI status was considered indeterminate.

## Analysis workflow

The public analysis begins with an already finalized, adjudicated gold-standard CSV and the JSON outputs produced by each model.

The script:

1. Reads the adjudicated gold-standard CSV.
2. Parses the PCI-identification JSON output for each model.
3. Parses the complex-PCI extraction JSON output for each model.
4. Matches model predictions to the corresponding gold-standard report using a report identifier.
5. Performs basic normalization of numeric, binary, and missing values.
6. Evaluates overall PCI identification performance.
7. Evaluates PCI identification performance by clinical site.
8. Calculates exact-match extraction accuracy for the six complex PCI variables.
9. Converts gold-standard and predicted variables into the six binary complex PCI criteria.
10. Derives gold-standard and predicted complex PCI status.
11. Evaluates overall and site-level complex PCI classification.
12. Evaluates classification performance for each individual complex PCI criterion.
13. Calculates site-level heterogeneity in accuracy, sensitivity, and specificity.
14. Generates the manuscript evaluation tables, source-data tables, and figures.

No raw narrative text is required by `analysis.py`.

## Required gold-standard data

The analysis requires a private CSV containing one row per report and the following columns:

```text
output_number
Site
PCI_performed
vessels_treated
lesions_treated
stents_implanted
total_stent_length_mm
bifurcation_with_2_stents
chronic_total_occlusion
```

### Column descriptions

| Column                      | Description                                                              |
| --------------------------- | ------------------------------------------------------------------------ |
| `output_number`             | Unique identifier used to match the gold-standard record to model output |
| `Site`                      | Clinical site                                                            |
| `PCI_performed`             | Gold-standard PCI status                                                 |
| `vessels_treated`           | Gold-standard number of vessels treated                                  |
| `lesions_treated`           | Gold-standard number of lesions treated                                  |
| `stents_implanted`          | Gold-standard number of stents implanted                                 |
| `total_stent_length_mm`     | Gold-standard total implanted stent length in millimeters                |
| `bifurcation_with_2_stents` | Gold-standard indicator for bifurcation PCI treated with two stents      |
| `chronic_total_occlusion`   | Gold-standard indicator for chronic total occlusion                      |

Other columns may be present in the private dataset but are not required by the analysis.

## Model output files

Two JSON output files are supplied for each model.

### 1. PCI identification output

The first JSON contains the model's determination of whether PCI was performed.

A simple supported record is:

```json
{
  "output_number": 1,
  "PCI_performed": "Yes"
}
```

`PCI_predicted` may also be used as the output field name.

### 2. Complex PCI extraction output

The second JSON contains the six extracted procedural variables.

For example:

```json
{
  "output_number": 1,
  "vessels_treated": 2,
  "lesions_treated": 2,
  "stents_implanted": 3,
  "total_stent_length_mm": 72,
  "bifurcation_with_2_stents": "No",
  "chronic_total_occlusion": "No"
}
```

The analysis parser also accommodates several common JSON storage formats, including lists of records, dictionaries indexed by report number, JSON responses stored as strings, and responses surrounded by Markdown code fences.

Every model output must contain an identifier that can be matched to the gold-standard `output_number`.

## Running the analysis

Install the required Python packages:

```bash
pip install -r requirements.txt
```

The analysis is run from the command line.

Each `--model` argument is followed by:

1. the model name,
2. the PCI-identification JSON file, and
3. the complex-PCI extraction JSON file.

For example:

```bash
python analysis.py \
  --gold-standard /path/to/private/gold_standard.csv \
  --model "Llama 3 70B" /path/to/llama_pci.json /path/to/llama_complex_pci.json \
  --model "Meditron-7B" /path/to/meditron_pci.json /path/to/meditron_complex_pci.json \
  --model "BioMistral-7B" /path/to/biomistral_pci.json /path/to/biomistral_complex_pci.json \
  --outdir results
```

The `--model` argument can be repeated for additional models.

The order in which models are provided is retained in the output tables and figures.

## Evaluation metrics

For PCI identification, complex PCI classification, and each individual complex PCI criterion, the script calculates:

* True positives
* False positives
* True negatives
* False negatives
* Sensitivity
* Specificity
* Positive predictive value
* Negative predictive value
* Accuracy
* F1 score

Wilson 95% confidence intervals are calculated for binomial performance measures.

F1 scores are reported as point estimates.

## Extraction accuracy

Extraction of the six complex PCI variables is evaluated among reports with gold-standard PCI.

For each variable, exact-match accuracy is calculated as the proportion of evaluable reports for which the model-extracted value matches the adjudicated reference-standard value.

## Site-level evaluation

Site-level analyses exclude reports without an available clinical site.

Overall analyses retain reports with missing clinical-site information when the report is otherwise evaluable.

Site-level performance is calculated separately for:

* PCI identification
* Complex PCI classification

## Site-level heterogeneity

Heterogeneity across clinical sites is evaluated separately for:

* Accuracy
* Sensitivity
* Specificity

For each metric, a Pearson chi-square test evaluates equality of proportions across sites.

The metric-specific denominators are:

* **Accuracy:** all evaluable reports
* **Sensitivity:** gold-standard positive reports
* **Specificity:** gold-standard negative reports

An I²-style statistic is also calculated as:

```text
I² = max(0, (Q - df) / Q) × 100
```

A result is reported as not estimable when the heterogeneity statistic cannot be calculated.

To generate CSV results without figures:

```bash
python analysis.py \
  --gold-standard /path/to/private/gold_standard.csv \
  --model "Model name" /path/to/pci_output.json /path/to/extraction_output.json \
  --outdir results \
  --skip-plots
```

## Private merged evaluation data

For local validation, the optional `--save-merged` flag saves the patient-level dataframe created after merging the reference standard with model predictions:

```bash
python analysis.py \
  --gold-standard /path/to/private/gold_standard.csv \
  --model "Model name" /path/to/pci_output.json /path/to/extraction_output.json \
  --outdir results \
  --save-merged
```

These files are written to:

```text
results/private_derived_data/
```

These merged files may contain protected study information and **should not be committed to the public repository**.

## Prompts

The `prompts/` directory contains the model instructions used in the study.

The prompts are organized according to the two primary model tasks:

```text
prompts/
├── pci_identification/
└── complex_pci_extraction/
```

The PCI-identification prompt asks the model to determine whether a report describes an actual coronary PCI procedure.

The complex-PCI extraction prompt asks the model to extract the six procedural variables required for complex PCI classification in a structured format.

The same task definitions were used across the evaluated models.

## Data availability and privacy

The cardiac catheterization reports and adjudicated patient-level reference-standard data used in this study are not publicly distributed because of Institutional Review Board and patient-privacy restrictions.

This repository is intended to make the **computational evaluation methodology, prompts, and statistical analysis transparent and reproducible** without releasing protected clinical data.

Researchers with appropriately structured local data can run the evaluation code by providing their own gold-standard CSV and corresponding model JSON outputs.
